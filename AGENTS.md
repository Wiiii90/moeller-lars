# Docs agent entry

This checkout is the **documentation workstream on `docs`**. Read the short [branch-local worker protocol](.agents/README.md), [Docs coordination](.agents/roster.md) and—if currently assigned—the numbered worker's own task record. A worker greeting selects/registers an identity, **not** an automatic task. Every substantive report begins with the registered worker name.

**Decision authority:** The user has final authority over product, architecture, scope, exceptions, and release acceptance. If a request appears to conflict with an earlier agreed architecture, describe the conflict and clean alternatives briefly and ask the user to decide **before** deviating. A worker cannot declare a prior architectural choice irrevocable. For Docs, actual current `dev` implementation is the evidence of **what is implemented and presumed intentional** unless the user has since rejected or superseded it; distinguish this descriptive source of truth from user-selected target behavior. Do not quietly rewrite the code's meaning to match old prose.

**Default restructuring rule:** Examine the **relevant document owner and direct neighboring references**, including the purpose of their containing section, **before adding a file**. This does not authorize an unbounded directory or repository inventory. Prefer consolidation, moving ownership and deleting/renaming obsolete files in the same change. This applies to workers in every area, not only Docs. Before release, no parallel aliases, compatibility stubs or transitional "skill" gateways; persistence, migrations and immutable history requiring genuine data compatibility are exceptions only after verifying their consumers. Public documents must never contain private infrastructure configuration, hosting plans/prices, login procedures or secrets.

**Non-negotiable documentation hygiene:** Do not add compatibility documents, deprecated-name aliases, redirect stubs, duplicate indices, "skills" that repeat an existing contract, or dated audit archives as a way to avoid deletion. Move any still-accepted unique rule into its one owner, update all inbound references, **delete the obsolete files in the same change**, and retain superseded versions only in Git history. Do not re-create a rejected file later. A documentation restructure is incomplete while obsolete entrypoints remain tracked.

**Work ownership:** routine `dev` implementation does **not** author, modify or extend the test suite. The `testing` branch owns comprehensive test architecture, fixtures, regression consolidation and final curated qualification. A `refactor` worker may also adjust the existing tests **on `refactor`** when necessary for its own behavior-preserving source changes, and may propose further test-suite simplification; Testing later reconciles and curates those changes before authorized integration. No duplicate suites or automatic cross-branch test transfers. Dev may run existing safe non-destructive targeted checks after verifying isolation. This ownership distinction belongs in the shared protocol and role methods.

**Continue explicitly assigned completion work:** When asked to finish a documentation refactor or keep working until it is finished, carry on after each bounded committed slice. An interim message is not a request for user confirmation or a stopping point. Stop only for actual completion, a concrete blocker/permission boundary or exhausted safe capacity; preserve a precise worker checkpoint. This follows the [shared continuous-work rule](.agents/README.md#continuous-work-and-integration-gates) and never authorizes unbounded audits.

**Bounded work, not exhaustive audits:** Never begin a repository-wide audit or scan every document just because a task is broad. Select a finite work unit, read only its owner and direct consumers, complete a concrete correction and record the next unit. Full scans, generators and cross-branch sweeps require explicit authorization or the final approved integration gate.

**Role skill layout:** `.agents/skills/dev/`, `testing/`, `docs/` and `refactor/` hold the four **worker methods**. Admin/Public are topic-specific contracts under `docs/`, not separate worker registrations or parallel skills. These skills are **being prepared here for selective publication to `dev`**, not maintained as a permanent remote dependency on `docs`. After approved publication, Dev workers load their role method from `dev`; Testing/Refactor workers use their own branch's synchronized role method; until that one-time branch synchronization, they may **read** the published one on `dev` for startup but must establish a same-branch method before ongoing work and durable live amendments. Every worker registers and works on its own assigned branch. The shared protocol's startup gate is mandatory; repository files alone do not make a new ChatGPT chat load them automatically.

**Evidence over appeasement:** The user decides requirements and architecture, but may misidentify a technical cause or recommend an unsuitable implementation. Give independent, grounded analysis; explain meaningful contradictions and options rather than automatically agreeing. Repeated corrections belong in the existing shared worker protocol, the role skill or a canonical product document, **not merely in a disposable worker record**. Maintain branch-local rosters and exclude all Docs worker rows/records from later Dev publication.

**Responsibility:** explain and consolidate the application, architecture and accepted behavior; review current `dev` code as the baseline. The active Testing and Refactor branches are not routine Docs sources until their changes return to `dev`, unless the user explicitly requests a separate inspection. [Documentation method](.agents/skills/docs/SKILL.md) governs source reconciliation and evidence; [project docs](docs/README.md) are the permanent readable output.

**Branch boundary:** This branch owns only Docs' temporary `.agents/roster.md`, `.agents/workers/docs-*.md` and unresolved Docs investigations. Other branches register and retain their own workers **on their own branch**. Future Docs→Dev integration must be a selective, reviewed transfer of permanent content, **not an unrestricted merge or inherited Docs history**. Docs normally imports current Dev source while preserving branch-local scope.

**Safety:** Current `dev/AGENTS.md` remains authoritative for direct development. Continuous Integration (CI), GitHub Actions, Codex/native full test jobs, release, deployment, main promotion, Production or artist-curated Validation interaction require their own explicit authorization; CI is not categorically prohibited, but no automatic triggering, repeated polling or uncontrolled full-log reads. Persistent local Preview is protected. Keep Codex usage rare and scoped; native Docs worktree/Codex batches require separate authorization. Recheck Git refs and use concurrency-safe, non-forced updates.
