# Documentation maintenance and source evidence

This is the stable procedure for the `docs` documentation workstream. **Live coordination and cross-worker work** belong in the [shared Docs area](../areas/docs.md); an individual worker record exists only after that worker is activated. Stable documentation methods belong here, not in worker memory. Root `AGENTS.md` supplies branch and safety rules.

## Routine source reconciliation

1. Resolve fresh `docs` and `dev` HEADs from GitHub and check `testing` when making test-suite claims. `dev` owns application implementation and interim tests; the **active `testing` workstream curates the intended canonical suite** for a controlled return to `dev` before cutover. A Testing Worker is a role, not automatically a branch authorization; the `refactor` branch was created from `dev@02004071` on 25 October 2026; Refactor edits and integration require a concrete task and separate review. No competing root policy.
2. **Regularly merge/reconcile current `dev` into `docs`** so documentation source inspections use current code, resolving overlaps by ownership; compare new commits with the last reviewed contract/evidence baseline and distinguish *source-sync completion* from *documentation-semantic completion*. Only use an individual worker record if that worker was actually opened. Triage affected files by existing [normative owner](../../docs/README.md) and [composed flows](../../docs/architecture/cross-feature-compositions.md); don't rebuild the full architecture after each commit.
**Additional test authority:** Compare the continuously curated `testing` branch whenever documenting test architecture, meaningful behavioral coverage, regression risk or test-execution claims. `testing` is based on incoming `dev` changes but may contain test-only commits not yet integrated back. Treat current `dev` as the application source and active `testing` as an additional test-evidence source; do not blindly merge the Testing branch into Docs, overwrite independently curated tests, or treat authored assertions as executed proof. Recheck both branch heads before summarizing.

3. Prefer current source/accepted product behavior over stale documentation, but separate **code present**, **authored assertion**, **actually executed test**, **browser reviewed** and **artist accepted**. Pin SHA of relevant source. Preserve historical inventory provenance; a regenerated image doesn't prove a live system.
4. Update the **one canonical owner** of each affected rule; retire contradictory old wording instead of appending a new changelog section. Link across subjects. Use lifecycle/end-to-end diagrams for meaningful transaction, read, render, failure and rollback boundaries; class/import diagrams are structural inventories only.
5. Keep the [architecture index](../../docs/architecture/README.md), [coverage/evidence matrix](../../docs/architecture/completion-criteria.md) and [shared Docs area](../areas/docs.md) consistent; any active worker updates only its own temporary record.
6. GitHub-only source/relative-reference checks are normal. Native PHP link checks/generator writes **only in a rare, expressly authorized Codex batch** in the existing `docs` worktree. No routine instructions asking the user to run local Docs commands.
7. Confirm HEAD again before a docs-only commit. If it moved, compare and reconcile, then write to existing `docs` using a normal fast-forward expected-SHA update. `dev` remains read-only unless the user separately authorizes integration.

## Worker memory and cross-workstream review

- Individual worker notes primarily track **the user's actual assignments, their exact current status, completed substeps, blockers and verified result**. Any other conversation context is included only insofar as needed to resume the assignment. Keep this scoped to the individual worker and no other worker's private file.
- Registration and sign-out are mandatory in the matching shared area file when a worker starts, pauses, is replaced, or retires. A complete retirement deletes the temporary worker file and unregisters its shared row in one guarded commit, **after** preserving durable knowledge.
- At the user's instruction, inspect **all relevant** currently activated worker records (including Dev/Testing/Refactor); identify generally applicable outcomes and consolidate them back to their canonical `docs/` design/feature owner or common procedure/skill. Protect other workers' active tasks and do not write their individual notes from a different worker identity unless specifically asked.
- Every worker should also propagate general, verified improvements to stable procedures, feature contracts and cross-worker coordination where applicable. Prefer updating the existing owner to creating a new category document.

## Documentation structure and continuous consolidation

- Docs reviews noteworthy incoming implementation and testing changes for documentation impact, then updates the **existing authoritative owner** instead of appending a dated source-delta section.
- Before editing any architecture document, **read the document as a whole**, determine its audience, questions and role relative to neighboring owners, and design the full outline and evidence approach. Do not append a small diagram or unrelated “overview” as a cosmetic repair. The [architecture document](../../docs/ARCHITECTURE.md) must ultimately offer a coherent, navigable system model, not a collection of arbitrary local observations.
- The intended architecture spans system context and deployment ownership, domain/composition boundaries, behavior across layers, request/event/data flows, persistent state, publication/recovery/concurrency, security and failure paths. Use a **connected narrative** with meaningful architecture views (component/context, UML class/package/state, sequence/activity, data model as appropriate), linking levels and explicit design choices. Diagram quality is measured by the nontrivial relationships and cross-boundary reasoning it reveals, **not number of diagrams**; three nodes illustrating an obvious function call add no value.
- Keep rich low-level detail where useful, but organize it behind an intelligible main architecture and topical reference documents. A reader should understand orchestration, why boundaries exist, and where to investigate without reading hundreds of unstructured paragraphs or reconstructing the narrative from implementation files.
- Classify every file as normative product behavior, architectural explanation, operational/test method, versioned source evidence or temporary working state. Labels and index must make these differences visible.
- Historic generators, diagrams and test inventories retain their actual source/verification version; do not imply current runtime coverage from old output. Defer destructive removal until all unique facts and incoming links have been checked and moved to the proper owner.
- Regularly remove overwritten rules, duplicate descriptions, old chat/process references and unnecessary temporary files. Use Git for history; do not create a new audit diary for the cleanup. Area-wide documentation debt stays in [Docs coordination](../areas/docs.md).

## Source and environment boundaries

- Inferred import, relation or method declaration is **not** an observed runtime call; Eloquent relation is not a physical PostgreSQL foreign key. Runtime controller/Livewire discovery, URL/asset policy and browser gestures require their respective evidence.
- Document Working, Committed/LIVE, checkpoints and immutable media/historical protection separately; avoid false claims from a clean-looking single render.
- A physical catalog export belongs to a fully migrated, **independently verified disposable** PostgreSQL only. The artist-curated Validation environment is protected cutover material, not a test database.
- Never run, inspect or operate Continuous Integration (CI); no deployment/release or Production/Validation writes.

## Integration boundary

The user's eventual `docs` → `dev` integration is a separate authorized task. Treat current `dev/AGENTS.md` as authority; preserve live `dev` worker and Rights state, and reconcile newer dev documentation by owner. This Docs-only change may remove old Docs root names but **cannot delete the corresponding files on `dev`** until the future integration. See the [single worker protocol](../README.md) and [shared coordination files](../areas/docs.md). Worker names provide context, never automatic permission to start a prior task; live records may contain open discussions without executable steps.
