# Branch-local worker protocol

This is the reusable lifecycle procedure. **Every worker belongs to one working branch**, never to a global roster on `docs`. Only actual activation creates an individual record. The four authoritative **role** methods are [Dev](skills/dev/SKILL.md), [Testing](skills/testing/SKILL.md), [Docs](skills/docs/SKILL.md), [Refactor](skills/refactor/SKILL.md). Admin/Public are **product topics** accessed from [the documentation index](../docs/README.md), not additional worker roles.

**Branch-specific coordination:** each working branch maintains its own roster and numbered worker records **only for actually activated workers on that branch**. The roster owns assignments and lease tokens; each worker record owns its own progress; this protocol and the role skill own the reusable method. No role's active roster is a shared or central registry. In particular, Docs' current roster/records on `docs` must not be copied to `dev`.

## Startup: one branch, local entry, no remote Docs dependency

The `docs` branch is the **preparation workspace** for reusable documentation and skill revisions. Once the user approves their selective publication to `dev`, `dev` owns the published shared `.agents/README.md` and `.agents/skills/{dev,testing,docs,refactor}/SKILL.md`. A new Dev worker reads `dev/AGENTS.md` and `dev/.agents/skills/dev/SKILL.md` **on `dev`**; Testing/Refactor workers read their own branch's `AGENTS.md` and same-branch role skill if present, otherwise the published skill on `dev` until their next source synchronization. Docs workers use their own `docs` branch entry and method. **Never bootstrap a permanent Dev, Testing or Refactor worker from the provisional `docs` branch.** Do not create duplicate skill implementations or alias bridges in an attempt to compensate for branch sync.

**Before investigating another branch, analyzing a user's task or promising changes:** identify the requested role and working branch; read its `AGENTS.md`, the indicated local/published role method and this shared lifecycle; inspect the *working branch's* roster; register or explicitly replace the numbered slot on that same branch with a checked lease. Only then report as the registered worker and proceed with the user's actual task. A missing method is a startup blocker to report, not permission to silently skip it. A first response can state the requested identity while registration is underway, but must not claim registration was completed prematurely.

**ChatGPT Project boundary:** repository files and Markdown `SKILL.md` files are not automatically injected into every new project chat solely because they exist in Git. The user must separately install a short bootstrap instruction in the ChatGPT Project settings (or another actually active project-level instruction source) telling new worker chats to open the correct branch entries and register **before working**; editing this repository does not change those ChatGPT settings. Do not report that one-time setup as done unless the settings were actually changed and a startup checked. The role skill and protocol supply the durable substance after loading.

## Activation, takeover and sign-out

1. On `Du bist ein neuer Testing Worker` or `Du bist ein Testing Worker`, select the **lowest positive unoccupied** number on `testing` and register it. The same rule applies to the other branches. A free number has no active `.agents/workers/<area>-N.md`.
2. `Du bist Testing Worker 1` selects or initializes slot 1 on `testing`; this may register an **already-running chat** using its own real current assignments and progress. It must not fabricate past tasks or automatically restart an old task. A second chat cannot silently take over an occupied slot.
3. `Ersetze Testing Worker 1` deliberately supersedes that slot's current chat. Increment the **monotonic lease token** in the roster and worker file together. Continue previous work **only** on an explicit continuation instruction.
4. **Sign in:** create the own task/progress record and a corresponding active roster row in one concurrency-checked commit on the **working branch**. Record the actual user assignments, status, completed steps, current evidence, blockers and outstanding actions, not a chat transcript. Do not store another worker's private tasks in this file.
5. **Sign out:** when a worker explicitly ends/retires, first consolidate verified durable findings into their owning product document or common workflow, and transfer any still-owned unfinished action to an explicitly identified owner. Then **delete the temporary worker file and remove its roster row/claims in one guarded commit**. Its number becomes free. A paused worker keeps its file and row until resumed or explicitly replaced/retired.
6. If a chat reaches its context limit without sign-out, the user can deliberately assign a replacement chat to the **same numbered slot**. It reads only the persisted task state and current Git source; unsaved chat details cannot be recovered.

Each branch-local roster owns its independent **next lease token**. A new allocation or replacement consumes this token (then increments it) even when a previously retired *number* is reused. A stale chat must reread its current branch's shared roster and personal lease token **before each write**, stopping if they no longer match. Reread the branch HEAD, compare other claims, and commit with an expected-head non-forced update; retry from fresh state on a race. This is optimistic concurrency control, not a physical Git lock.

**Every substantive worker report starts with its exact registered identity** (e.g., “Docs Worker 1”). A named role or saved next step does not itself authorize code changes, tests, merges or automatic task execution.

## Branch-local roster initialization and cross-branch exclusion

**Every working branch should retain one tracked, branch-local `.agents/roster.md`**, even before its first worker is activated. If a branch has no real registry yet, initialize an **empty** one with a branch-specific heading, `**Next lease token:** 1`, the columns `Worker | Lease | State | Claimed work | Own task record` and no worker rows. Do not pre-create any `.agents/workers/<role>-N.md`: an individual file means that numbered chat was actually activated. Each branch maintains its independent monotonically increasing lease sequence. When all workers sign out, the empty roster remains.

**For the future approved Docs-to-Dev publication:** bring the reviewed shared protocol/skills across, but **never** bring Docs' active worker rows, lease counter or individual Docs records. Retain a verified existing Dev roster if present; otherwise initialize **one empty Dev roster**, not both a Docs copy and a Dev copy. Testing and Refactor likewise receive their own empty roster during their authorized method synchronization if missing. No unfiltered branch history merge and no transfer of another branch's `.agents/workers/` directory. This is an explicit transfer gate, not a promise that other branch trees were already changed.

## Clear user-facing language and evidence

For each standalone user-facing report, answer and worker handoff, **write out technical abbreviations on first use and explain unfamiliar terms briefly in plain language**. This includes initialisms for protocols, tooling and file formats. Keep literal source identifiers, file paths, configuration keys and existing interface labels unchanged; explain them next to the identifier instead of renaming code. A long chain of unexplained acronyms is not evidence of progress. If an expansion is uncertain, verify it or use an ordinary descriptive expression.

## Durable corrections, user authority and technical disagreement

The user has the last word over desired features, product decisions, architectural exceptions, freeze and transfers. A user's diagnosis, proposed implementation, attribution of fault or assumptions about a programming language can still be mistaken. **Do not automatically agree or flatter.** Identify the concrete evidence and owner, explain when an approach would contradict existing design or technical facts, suggest the smallest sound alternative, and let the user decide a real conflict. Never implement a workaround silently just to avoid disagreement.

**A repeated correction must survive this chat.** Determine its actual owner:
- Cross-role onboarding, worker identity, branch isolation, finite investigation and feedback handling -> amend **this protocol**.
- Role-specific method (central implementation, meaningful testing, refactoring discipline) -> amend the relevant **existing role skill**.
- Accepted feature, UI or architectural invariant -> amend the one relevant **permanent product/architecture contract** through the Docs publication boundary.
- Temporary assignment/incident/progress -> update **only this branch's current worker record**.

**During the same task in which a reusable correction is learned, update the existing skill/protocol section on the worker's own working branch when it is there and within scope**; do not wait for a Docs Worker or let the only copy live in ephemeral notes. If the shared owner is not on that branch, keep an exact proposed change for the Docs owner and propagate it during an approved synchronized transfer. Docs later checks these live amendments for consistency, centralizes shared rules and removes duplicates. A new rule takes effect for other branches **only after** that reviewed propagation, not by virtue of the chat saying it has been learned. First inspect the existing section so the new lesson is a **precise amendment**, not another contradictory appendix or redundant skill. In other-branch/shared ownership cases, record a concise proposed change and route it through the reviewed Docs/Dev transfer; do not mutate another branch's private worker data or spin up a parallel policy file. If the user requests a rule contrary to an earlier accepted one, explain the conflict and request the user's choice. Not every individual complaint merits a new universal prohibition.

## Cross-worker responsibilities

- **Dev workers:** implement and source-review application changes on `dev`. **Do not create, modify, refactor or delete tests or routine general documentation.** Update active scoped living workstream records instead; report exact source commit, affected behavior/consumers, verification actually performed, changed contract semantics and the test/documentation follow-up. Explicitly requested targeted documentation work is distinct.
- **Test workers:** own the canonical test design, fixtures, regression cleanup, browser automation and curated qualification on `testing`, following their own branch's `AGENTS.md`. **Refactor workers may update affected tests on `refactor`** to preserve behavior under their source changes and may simplify flawed existing cases; Testing retains responsibility for later holistic test-suite reconciliation. A test edit is never permission to move another branch's worker files or introduce a duplicate runner. Later integration of reviewed tests into `dev` is a separately authorized transfer.
- **Docs workers:** maintain one authoritative document per subject, current navigation and concise shared method. **Delete obsolete files and update every inbound link in the same correction**; no historical `-skill.md` roots, redirect/alias stubs or new appendix archives to compensate for deletion. Git history stores retired texts. Worker progress belongs only in active numbered records.
- **Refactor workers:** inspect the architecture and real source for structural mistakes left by other workers (duplicate owners, `fooWithThis` variants, needless compatibility bridges, coupling, incoherent responsibilities and brittle tests), and make bounded behavior-preserving corrections on `refactor`. They may maintain tests affected by those corrections and request authorized Codex execution when necessary, without creating a second test suite. **All workers:** operate on their assigned branch and improve reusable rules in the existing local role skill/shared contract during relevant tasks instead of recording lessons only in a disposable worker file.

## Continuous work and integration gates

The **user decides** the scope, architecture, deviations, timing of freezes, acceptance and integrations. Source and existing contracts show the implemented state; bring conflicts back to the user rather than autonomously treating an old decision as final. A worker's architecture warning should name the failing invariant and feasible options, not stall with speculative concerns.

Usual **direction of gated progress** is `dev → testing → docs → refactor → main`, **not a mandatory single-chain merge of commit histories**. The user may work with Docs, Test or Refactor workers in parallel with many scoped Dev workers. Those branches may continuously reconcile newer `dev` code **as preparatory work**, without running full acceptance or demanding Dev stop on every commit.

- **Dev iteration:** parallel Dev workers change application code on `dev`, coordinate ownership and reconcile each other's commits. Do not write general `docs/` contracts, tests or generated manuals as part of routine feature work; keep the **active living workstream/task record** current in the same scope. Report behavior/API/architecture changes and required test/documentation follow-ups. A deliberately requested, scoped documentation correction remains an explicit exception.
- **Testing preparation:** record the last integrated source baseline and compare the **entire accumulated Dev diff**, including config, migrations, controllers, shared components and test dependencies. Reconcile source into Test's working tree under its own branch rules, then redesign the existing test suite **holistically** before adding cases: merge related fixtures, retire obsolete tests and move cases to the appropriate layer. No new parallel test frameworks or repair-specific test piles merely to keep historic names.
- **Testing final gate:** **only after the user freezes Dev**, make Testing source-equivalent to that exact frozen Dev commit, except Testing-owned tests and isolated test support. Check actual file/tree differences, not just ahead/behind counts. Use authorized Codex/native execution in a positively isolated environment for the **final pre-integration run**, correct the test suite on Testing, rerun necessary failures, and report actual results and unresolved product defects. A product defect goes back to Dev for correction; synchronize the new frozen baseline before repeating the gate. Curated tests return through a reviewed integration, never a casual branch merge carrying worker files.
- **Docs final gate:** Docs may review/reorganize in parallel against accepted `dev` source. Before Docs transfer, reconcile all incorporated application/test changes, finish documentation/source/link accuracy, and only then use authorized Codex/native generators or checkers **if the retained docs actually require generation**. Review resulting artifacts and remove obsolete outputs. Transfer only reviewed durable docs; never merge branch-local workers or histories.
- **Refactor and main:** Refactor may prepare concurrently but behavior-preserving changes are reconciled against the post-Test/Docs accepted baseline, verified and reviewed before selective integration. Promotion to `main` needs the user's explicit final approval and separate release/security checks. The stage order may change at the user's direction; an earlier stage is **never implicitly approved** by another stage's progress.

**Structure and deletion rule for every worker:** before creating a module, file, tool, test fixture, document or index, ask whether an existing owner should instead be reorganized, renamed, moved or removed. Remove superseded implementations/references in the same scoped change. Do not install adapters/aliases/compatibility shims for incomplete pre-release source merely to avoid changing callers; preserve actually persisted database/migration/snapshot compatibility when essential, and explain any proposed exception to the user.

## No exhaustive audit by default

Workers must scope each request to the **smallest complete architectural owner and its direct consumers**. Do not scan all repository files, run broad inventories, read every manual or conduct a full test/generator sweep just to establish context. Use bounded batches, make a coherent change, stop and retain only actionable next steps. Whole-repository qualification is an explicit user-approved task or a final integration gate, not routine investigation.

## Codex and Continuous Integration resource policy

Codex is a comparatively expensive execution capability: prefer scoped source inspection and small safe checks first, and **request/use Codex only when its actual execution or modification capability is needed and approved**, especially for isolated test runs or test-source changes in Refactor/Testing. Before an approved integration/merge, the responsible worker can request a concentrated final Codex/native qualification batch rather than repeatedly running exhaustive suites during daily edits. Any database-writing run must prove independent disposable database/file isolation before execution; do not touch protected Preview/Validation/Production data.

Continuous Integration (CI) and GitHub Actions are **not globally banned**. Trigger, inspect or use them **only when the user specifically asks or authorizes that workflow** (for example a final integration gate). Because long-running CI polling and oversized job-log responses have exhausted chats, **never start indefinite status polling or stream entire logs into conversation**. Prefer a bounded check of the final run summary, failed job/step and narrowly relevant error excerpt; report that results are pending/unavailable when no bounded result exists. User approval for a merge does not automatically authorize unrelated CI, infrastructure or deployment actions.

## Knowledge and ownership

- Personal record: **this worker's actual assignments and progress**. Keep it short and replace superseded text at milestones.
- Roster: sign-in/sign-out, claimed file/feature scopes and coordination among workers **on this branch**. Do not copy entire assignments into a second file.
- Durable `docs/` and project procedures: accepted design, system behavior, architectural decisions, testing method and reusable process. A worker promotes verified lasting findings to the existing owning document; it does not preserve useful knowledge only in disposable memory.
- Git history: previous records are recoverable within the originating branch, but are **not** a substitute for current tasks or an automatically runnable handoff.

## Branch integration — prevent temporary files from escaping

**Never merge a worker-bearing branch into another branch using an unrestricted Git merge.** A deletion before merge removes the file from the final tree **but not from the merged commit ancestry**. `.gitignore`, a normal `.gitattributes` setting or a last-minute cleanup commit do not provide historical isolation.

- Bring newer `dev` application changes into `docs`, `testing` and `refactor` through an owner-reviewed source synchronization. If `dev` already contains private Dev-worker commits, use a **filtered source transfer** rather than a full ancestry merge; verify actual source parity, not a misleading ahead/behind count.
- Bring completed `docs` changes back to `dev` with a **reviewed, path-filtered commit built on the current `dev` HEAD**, retaining `dev` code, active Dev-worker state and root branch policy. Import the approved *durable* documentation **and the shared protocol/role skills** to their real paths under `dev/.agents/`. Do **not** merge `docs` history into `dev`. As part of the same user-approved publication operation, update `dev/AGENTS.md` through a separately reviewed branch-local change to use `dev/.agents/skills/dev/SKILL.md` and `dev/.agents/README.md` rather than URLs under `docs`; make corresponding own-branch entry updates on Testing/Refactor when their working branches receive the shared methods. The path-filter transfer guard excludes imported `AGENTS.md`; that restriction is not a reason to leave obsolete remote bootstrap links behind. Verify actual target file existence and entry links before claiming the handoff complete.
- Likewise, return verified `testing` tests and `refactor` code to `dev` as curated changes without importing their rosters, individual notes or unrelated branch policies/history.
- For `dev` → `main` cutover, use the same filtered release/export gate and **verify that the resulting tree and imported ancestry contain no worker records or branch-local rosters**. Do not treat a full `dev` ancestry merge as privacy-safe merely because a file was deleted.
- **Allowed to cross branches** only after review: permanent feature/architecture documentation, shared procedures and skills which are valid for the destination, and accepted application/test changes. **Must remain local:** `.agents/roster.md`, `.agents/workers/`, branch-specific `AGENTS.md` and temporary `.agents/topics/`/investigation notes. Docs-only helpers also need an explicit justification before export.

Implement the integration as an explicit reviewed Git diff/commit, check tracked paths and target branch tree before advancing the ref, and keep the target's own agent scope unchanged. No automatic branch promotion or CI interaction is authorized by this protocol.
