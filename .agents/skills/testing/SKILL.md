# Testing worker — test ownership

Read `testing/AGENTS.md`, [the worker lifecycle](../../README.md), the existing [test strategy](../../../docs/operations/testing.md), `testing/tests/README.md` and `testing/tests/Pest.php` as relevant. A numbered Testing worker registers its role and active task **on testing**, not in the Docs roster. This method restores the durable principles of the retired root `TESTING_SKILL.md`; that old root file must **not** return.

## Bounded cumulative-source procedure

For an explicit end-to-end assignment, **continue automatically through subsequent already-authorized finite work batches after each result and report**; no interim success summary ends the assignment. Stop only on real completion, an external approval/blocker or insufficient safe session capacity, then preserve the exact resumable state. This follows the [shared continuous-work rule](../../README.md#continuous-work-and-integration-gates) and never authorizes unbounded audits, unsolicited exhaustive tests or CI polling.

1. Find the exact last reconciled `dev` source SHA and inspect the **cumulative relevant changes** to the newest `dev` source; follow entrypoints, migrations, shared consumers and framework changes. Do not create a test for every Dev commit and do not scan unrelated repositories or execute an entire suite as a first step.
2. Map changed behavior to the **existing canonical suite and fixtures**. Before creating files, consider reorganizing, moving, consolidating, renaming or **deleting** obsolete tests; eliminate duplicated source-string assertions, cosmetic button/CSS-position regressions, stale incident scenarios and alternative test runners.
3. Preserve the same testing architecture: Pest **Unit** (pure), **Integration** (services and database/files), **Feature** (Admin/Public HTTP and authorization), **Migration** (actual cutover contracts), JavaScript unit tests and Chromium Component/End-to-End/Profiling projects. Dedicated multi-process PostgreSQL Publication and Public Session concurrency runners are **not** implied by standard Pest/CI. Discovery belongs to `tests/Pest.php`, `phpunit.xml` and the current Playwright config.
4. Protect real persistence/Working-versus-Committed behavior, security/authorization, immutable media, atomic audit/Undo/rollback, exactly-one success notification per real change, no-op and failure feedback, HTTP/session lifecycle and justified concurrency. Test meaningful public outcomes, not ephemeral repair rounds or implementation spelling.
5. Keep preparation bounded. Reconcile source on testing without claiming qualification. Only after the **user freezes dev** verify exact non-test source parity and run authorized full/relevant Codex/native suites as the last pre-integration gate. Fix erroneous tests **on testing**; true production defects return to Dev. Reconcile and recheck if Dev changed, then seek explicit transfer approval.

## Curate the suite, do not accumulate regression debris

The separate `testing` branch prepares the **eventual authoritative test suite** for all cumulative Dev changes. The suite currently on Dev may be transitional; it is not an immutable collection of cases to copy blindly. Test workers actively **refactor test architecture**: remove obsolete tests, merge related cases, simplify fixtures and reassign scenarios to their meaningful layer. Protect important invariants, not the filenames or implementation details used by past repair rounds.

**A finite reconciliation batch has these steps:**

1. Establish exact last reconciled Dev source and newest Dev commit. Inspect the **cumulative affected source diff**, including relevant shared consumers, migrations, configuration, services and feature flows; don't reason from commit messages or one bug report alone.
2. Match the changed behavior to existing test owners and layers. Decide first whether a current case can be modified or consolidated. New test files, fixtures or runners need a **distinct responsibility**, not just a new regression anecdote.
3. Choose durable user/domain guarantees: persisted edits and reload, validation, authorization, Working versus Committed, Preview exceptions, history/Undo/rollback, media reference lifetime, audit/notification boundaries, negative and true no-op behavior, or an actual concurrent race when relevant.
4. Remove tests that only check an incidental button location, CSS property, source spelling, class name, private method call, harmless markup reshuffle or one-off incident implementation. UI tests should assert **observable interaction** (focus, accessibility, navigation, state, modal lifecycle), not arbitrary geometry constants.
5. Share canonical setup and fixtures; don't add another test framework, runner or layer unless the current suite demonstrably cannot express the verified scenario. Avoid excessive mocking that bypasses the mutation or storage behavior being claimed.
6. Review net test changes for duplicate assertions, flakiness, vacuous passes and obsolete expectations. A genuine application defect goes back to Dev with precise reproduction; **never bend assertions just to make the suite green**.

**Layer selection is deliberate:** pure logic to Unit, persisted domain/file/transaction behavior to Integration, user-facing HTTP/Filament/Livewire behavior and permission checks to Feature, real cutover contracts to Migration, JavaScript state/lifecycle to JavaScript, browser-only interactions to Chromium. Special Publication and Session races require their dedicated **real multi-process PostgreSQL** runners and positive isolation; ordinary in-memory feature tests cannot claim that coverage. Do not duplicate the same scenario at every layer just to increase counts.

**Timing:** preparatory work may continue in small batches as Dev evolves. Repeated full-suite runs during that stage are wasteful and are not acceptance. Only the user-approved **Dev freeze** triggers exact non-test source parity verification and permitted final exhaustive qualification, followed by reviewed selective transfer. A test count or assertion count is never a source-coverage percentage and never a substitute for a demonstrated product behavior.

## Mandatory isolation

Database-writing tests and seeded browser tests require verified, **independently disposable PostgreSQL 17**, dedicated database/user/loopback port, temporary storage, no persistent volumes and an initially empty schema. Verify actual PDO/database/user/version/cluster identity **and the effective Laravel/PHPUnit `APP_ENV`/database connection** before enabling disposable test flags or destructive commands; an environment-variable label, Compose name or successful process exit is not isolation evidence. Clear inherited `DB_URL` and config cache; isolate upload/media directories, sessions, cache, views, logs and system temporary files; preserve `LocalPreviewDatabaseGuard`. Never wipe persistent Preview/Validation/Production or the user's Compose data volumes. Specifically, the persistent local Compose database `moeller_lars_testing` and named volume `moeller-lars_postgres_data` are **not disposable test targets**, despite the database name: never invoke `migrate:fresh`, `reset` or `db:wipe` against them. Before allowing any destructive test/reset, verify the actual SQL/PDO environment and independently owned ephemeral storage. Preserve unknown stashes/files; clean up only verifiably owned disposable test resources. A zero exit code does not prove containment.

The dedicated runners `tests/Support/RunPublicationConcurrency.ps1` and `tests/Support/RunPublicSessionConcurrency.ps1` must be invoked only on authorized, separately isolated Windows environments when qualifying their scenarios. Normal in-memory Pest sessions **do not** prove database-backed HTTP session races.

## Retain testing lessons outside short-lived worker records

When the user corrects recurring test design, isolation, scope or execution mistakes, update this **branch-local synchronized role method during that task** or the canonical [test contract](../../../docs/operations/testing.md) in its authorized owner, not a bug-specific appendix, duplicate suite or personal task diary. Distill a reusable rule with a concrete test-design consequence, check whether it contradicts older instructions and explain the conflict before changing accepted behavior. Testing owns the **canonical curated suite** on `testing`; a Refactor worker may edit tests on `refactor` as required by its own structural change. Testing reconciles those relevant improvements later, avoiding duplicated cases, incidental regressions and wholesale branch merges. Shared workflow revisions are reviewed for eventual publication on `dev` without importing another branch's worker files. User reports may identify real gaps but may misdiagnose their cause: verify source and runtime evidence rather than agreeing reflexively.

## Evidence, privacy and transfer

Always separate **source reviewed**, **test authored**, **test actually run**, **real browser checked** and **user accepted**. Report executed commands/results, skipped suites, coverage limitations and exact source SHA. No fake percentage from assertion count: combined PHP `app/` line coverage requires a real PCOV/Xdebug driver and applies only to PHP code; browser/JavaScript and special concurrency runners are not included, and no arbitrary release coverage threshold should be invented. CI/Actions, pull-request/promotion, release and production operations require separate authorization; CI is allowed when specifically requested, but never start unbounded polling or ingest complete multi-minute logs into chat. Codex costs should remain low: use narrowly when actual authorized execution/modification is needed (especially final pre-integration qualification), not on every source sync. A final gate can include both targeted and necessary full runs after a user-declared freeze. Include only curated changed test sources/necessary support on approved transfer; do not merge branch-local rosters or duplicate historical root skills.

No pre-release compatibility aliases, duplicate test suites or convenience frameworks. Preserve actual migration/snapshot/database compatibility. The user owns architectural exceptions, freeze and final test acceptance.
