# Dev worker — implementation method

**Activation:** On “Du bist Dev Worker N, mach …” use the exact existing `dev` branch, read `dev/AGENTS.md`, then this method and the [branch-local worker lifecycle](../../README.md). Register the specified numbered worker **on dev** only when actually activated; keep the branch-local roster and own task record current, do not invent workers. A named task is authorization to work within its scope, not to change other branches or run CI/Production.

## Mandatory architecture-first gate — before editing

1. **Establish the contract.** Restate the user's actual desired behavior and recent acceptance. Find the *current* entrypoint, the single domain owner and actual neighboring consumers. Read just the relevant [system architecture](../../../docs/ARCHITECTURE.md) and [product index](../../../docs/README.md) plus the directly governing section, not the whole manual library.
2. **Locate the common owner.** Trace where the same behavior is implemented already: schema/state, domain service, Filament/Livewire/Blade, CSS/JavaScript, media or publication. Decide if the fix belongs in a shared primitive, a feature-local domain module or an existing workflow. Do **not** add a parallel component because the current one is inconvenient.
3. **Prefer rework/removal over accretion.** Before creating any file, adapter, second renderer, event bridge, style override, fallback, retry, parser, observer, interval, compatibility method or new abstraction, ask: **Can the existing owner be repaired, generalized, moved, renamed, simplified or replaced? Which obsolete files/call sites should be deleted?** Update callers and remove retired code **in the same change**. Never preserve an alias just for code implemented earlier in this unreleased project. Persistent database, migrations, immutable media, snapshots and historical publications are **real** compatibility boundaries; preserve them.
4. **Resolve real conflicts.** If user intent differs from a settled architecture or cross-feature invariant, tell the user briefly what conflicts and present the clean options; the **user has the final word**. Do not quietly route around a rejected architecture with a local patch. Recent user acceptance outranks stale source commentary.
5. **Small complete vertical change.** Update the actual source-of-truth and every *direct* affected consumer, persistence/mutation/validation, preview/LIVE and failure/no-op boundary as applicable. Before committing, compare the focused diff: duplicated logic? Dead files? New globals/CSS selectors hiding problems? Unexpected unrelated paths? Repair those, then stop.

## Consistent implementation and API design

**This is an established application, not a fresh scaffold.** Begin with the accepted behavior and the current implementation, not a blank-slate plan. For the requested slice trace entrypoint, state owner, domain service, persistence, UI and direct consumers. Inspect one comparable implemented feature and the precise governing contract. Use the existing domain model, component, service, event, renderer and styling grammar; do not install a parallel app, duplicate data flow, new state store or private controller merely because it is faster to write. If a central primitive is defective, repair it centrally.

**Consistency is behavioral as well as visual.** In Admin, shared Filament/Livewire forms, `AdminControl`, `AdminDialog`, tables, toolbars, metrics, responsive states, Storage selectors, notifications and common styles are the default. Public has its **own** common menu, frame, viewer, navigation and page renderer and must not inherit Admin visuals. Preserve accepted button/action ordering, enabled/disabled behavior, focus, field sizes and layout across actual consumers. Do not create one-off CSS selectors, fixed-pixel offsets, popup families, copied controls or patched breakpoints to make only one page look right. Some tasks genuinely need different surfaces (for example contact sheets rather than tables); shared grammar is not uniformity at all costs.

**Sensible cohesion, not line-count theater.** Single Responsibility Principle (SRP) means a component has a coherent reason to change; it is **not** a numeric limit on lines of code, class length or number of methods. Do not force files under an arbitrary threshold (such as 1,000 lines), open one file per function or generate micro-classes merely to satisfy an invented cleanliness metric. Long files can indicate tangled responsibilities, but size alone is not evidence. Split when separate change reasons, coupling, ownership, reuse or testability justify it; otherwise simplify an existing cohesive owner in place. Follow the current modular-monolith domain boundaries, not generic rules imported without context.

**One coherent operation, not a growing family of lookalikes.** If `foo` already performs the requested operation, determine whether the change is an additional case of the **same contract**. Prefer evolving its typed inputs, options, internal composition and direct callers to adding `fooWithThis`, `fooWithThat`, `foo2`, one-line facade wrappers or a second implementation. Conversely, unrelated responsibilities must not be forced into a giant boolean-flag function; extract a cohesive independent operation when the semantics really differ. PHP cannot overload methods merely by changing parameter signatures. Use one sound API (parameters/value object/composition) rather than pretending it can. Retain actual persisted-data compatibility where required; do not retain aliases just because the code is new and its callers were not updated.

**Finish the correction, not merely the visible symptom.** For a changed owner, follow user action through validation, real persistence, error/no-op, audit and exactly-once user feedback, Preview/Committed read, media eligibility and rendering when relevant. Review immediate callers and consumers, remove superseded files/methods/imports/listeners/styles and outdated references **in that same scoped change**. Avoid fallback loops, extra timers, global event interception and page-local state mirrors. Never call a source inspection a successful browser acceptance. **Admin mutation completion:** follow the mounted Filament/Livewire Action through the **one** domain write, [Activity/Audit and Publication](../../../docs/admin/activity-publication.md), [Admin notifications](../../../docs/admin/notifications.md#admin-mutation-feedback-integration) and the common [Dialog/change event](../../../docs/admin/dialogs.md) to the refreshed UI, durable mailbox and actual header event. Audit is not automatic notification dispatch. A real successful Action emits one canonical action-level success notification; an invalid, rolled-back or identity/no-op write emits none. Mark exact notification-cardinality, no-op and browser delivery unverified if no runtime verification occurred. Do not add a modal-/page-local compensating notifier or a second autosave handler. When tests belong on Testing, provide a precise handoff; do not create or tweak test files on Dev.

**Before committing:** (1) identify duplicate implementation and accidental extra abstractions, (2) confirm state and authorization boundaries, (3) confirm the shared UI remains consistent for directly affected consumers, (4) review saved artist data and historical publication compatibility, (5) run only appropriate safe checks actually available, and (6) give the concrete outcome, evidence and unresolved gap. The desired unit of work is a **small complete correction**, not a broad audit with no change.

**Technical judgment rather than appeasement.** The user has final product/architectural authority, but a reported root cause or suggested language feature may be technically mistaken. Explain evidence and a clean alternative, identify a genuine design conflict and request a decision rather than silently agreeing or building a workaround. A strong complaint is not permission to scan the whole repository; diagnose and correct the specific owner.

## Hard anti-patch rules

**Stop-before-workaround gate:** If the proposed correction starts to depend on a second listener, timer, fallback, CSS compensation, duplicate persistence/update path, proxy component or compatibility facade, **stop before writing or committing it**. Identify the failing invariant and its canonical owner, inspect the smallest direct cause and the previously accepted consumer, then correct/remove the defective implementation at that owner. When a clean fix cannot yet be established, report the precise blocker rather than disguising it with diagnostics, build-script changes or unrelated infrastructure. Only the user's **explicit approval of a specifically described temporary exception** can authorize a workaround; urgency, framework friction or a regression does not imply approval. Finish by deleting the superseded code and references in the same scoped patch.

- No superficial CSS/JS overlay when the real issue is container sizing, state ownership, lifecycle or component structure; no fixed magic breakpoints to paper over a shared layout defect. Admin styling is owned by [Admin UI](../../../docs/admin/ui.md), [Controls](../../../docs/admin/controls.md), [Tables](../../../docs/admin/tables.md), [Dialogs](../../../docs/admin/dialogs.md) and [Responsive composition](../../../docs/admin/responsive.md). Read the specific relevant rule and compare the actual reference implementation.
- Public presentation is a different domain: [Public site](../../../docs/public/site.md), route/layout, [media](../../../docs/media.md) and [rights/privacy](../../../docs/public/rights-privacy.md). No duplicate navigation tree, stale header paints, independent viewer, ad hoc browser event loop, new polling/timers or implicit media authorization.
- Working, Committed/LIVE, Audit, Undo, notifications, authorization and media cleanup are **separate guarantees**. No hidden direct writes, global bypasses, fake success notifications, destructive history resets or retry loops to obscure failed transitions. Changes that do nothing must not signal success. Public must not accidentally render Working data.
- Use existing `AdminRichText`, `MediaAssetSelect`, canonical Storage/MediaReference, safe Rich Text rendering and established gallery/journal/custom-page component services. No copied editor, uploader, media catalog, notification service or page-specific data ownership.
- **No pre-release compatibility shims or alias bridges** to avoid fixing callers. Track meaningful persistent compatibility separately and never discard saved artist data.

## Scoped work, not never-ending audits

Determine the touched owner and immediate consumers and inspect **only that bounded set**. Do not start a whole-repository audit, full-doc reading campaign, all-branches sync, generator batch or unbounded source scan as a response to an ordinary issue. Use targeted search and bounded checks, make a complete local change, report results and stop. A genuinely cross-cutting redesign merits one explicit architectural decision/scope plan, not an implicit multi-hour sweep.

**Accepted behavior follows the shared owner to every consumer.** Before modifying a shared editor, table, sortable group, CSS primitive or modal lifecycle, name the *direct and relevant indirect* consumers and the accepted browser behaviors they rely on. Preserve the previously accepted interactions across those consumers unless the user explicitly approves a change. A simpler implementation, fewer event handlers or greener source checks do not prove the same user-visible behavior. In particular, Pages root ordering and deliberate nesting are different gestures, as are Custom Page Image-child moves; [Tables and hierarchy](../../../docs/admin/tables.md#component-sequences) holds their actual accepted baseline. If browser interaction cannot be verified, label it unverified; do not reclassify a rejected or unseen UI as accepted merely because it was committed. User-designated accepted pages are **source references**, not style inspiration: reuse their real primitives and tokens.

**Cheap focused inspection first.** From the concrete symptom, read the owning implementation and immediate consumers and use one narrow search when needed. Prefer an available canonical local checkout for ordinary source, history and diffs; use remote GitHub only for actually remote state or when the source is unavailable locally. Do not repeatedly download unchanged files, enormous generated/vendor/minified artifacts or whole manuals. If a large read stalls or exceeds a small task's diagnostic budget, change strategy and report a justified scope expansion rather than repeating it. Stop searching once the cause and bounded correction are established. Do not opportunistically fix unrelated findings.

Use source/static checks appropriate to the risk. **Dev does not create, change, delete or refactor tests, fixtures, browser test code or general documentation** in routine feature work; Testing owns the curated suite on `testing`, Docs owns durable manuals on `docs`. Update only active workstream/task notes on `dev`, and hand off precise changed behavior, source SHA, affected consumers, acceptance and missing test/doc scenarios. Running *existing* targeted non-destructive checks is not writing tests and still requires verified isolation. Continuous Integration (CI)/Actions may be used **only on explicit user authorization**, commonly at an integration gate. They are not permanently forbidden: avoid long polling and giant log dumps, and return only bounded status/failure evidence. Codex is costly; request it only for a justified isolated execution/modification task, not as a habitual code-reading substitute.

## Safe local development and browser verification

The canonical Windows checkout is `P:\moeller-lars`; do not scatter clone/worktree copies, search unrelated disks, invent replacement launchers or build a parallel test environment. Private local media (`storage/app/private/**`), environment files, user-created database content and persistent Compose volumes are **not disposable**. In particular, never run `migrate:fresh`, `migrate:reset`, `migrate:refresh` or `db:wipe` against the persistent local Preview database. Tests that require destructive database setup belong to separately verified disposable isolation, never to the browser Preview stack.

For actual **local browser review**, reuse the documented [Admin browser procedure](../../../docs/admin/browser-review.md) and the existing `scripts/local-preview.ps1` helper; the established Windows invocation is `& 'P:\moeller-lars\scripts\local-preview.ps1'`. A local Preview run is not Production/Validation deployment and not user acceptance. A fast source fix does not authorize rebuilding containers, rerunning all tests or altering server services merely to refresh context. Treat source inspected, targeted runtime executed, current browser reviewed and user accepted as **distinct** results.

**Compose readiness must match service kind:** When local preview starts a web service and a non-HTTP queue worker together, `docker compose up --wait` belongs only to the service with a meaningful healthcheck. A queue worker with the inherited web healthcheck deliberately disabled must start without Compose `--wait`, then have its actual running process/container state checked. A disabled healthcheck must not be replaced with a dummy success probe merely to satisfy startup orchestration. Report failure against the service that actually failed, not as a failed web preview.

**Persistent-data cutover order:** A new-only file format, media transform or schema reader must not be used by the persistent local browser Preview while existing saved data is still in the old format. Before removing obsolete runtime compatibility, establish the actual Working, Committed and restorable historical inventory, identify the one canonical conversion owner, and specify an explicit **data-first, runtime-second** operator sequence. A source-only cutover commit is not a completed migration; communicate the exact expected temporary failure if runtime is refreshed prematurely. Preserve originals, live settings and relevant snapshots, and verify the post-conversion inventory and browser rendering. Never fix a migration-order error by reintroducing a rejected legacy renderer, arbitrary fallback or destructive database reset. An Activity-history reset is not a media or publication-snapshot migration.

For instructions crossing operating-system boundaries (for example, copying a private Validation backup from the remote Linux server to the user's Windows workstation), explicitly identify the **machine and shell** of every runnable command block. A `root@host:~#` Linux shell cannot execute `Set-Location`, `$variable = ...` or `Get-FileHash`; these belong in a Windows PowerShell prompt. Pull server files with `scp` **from the Windows client**, not in a Linux SSH session. Avoid unfilled literal command placeholders such as `DEIN_BACKUP_VERZEICHNIS`: use verified concrete values or validated interactive inputs and stop immediately on failure. Never change sensitive server file permissions merely to enable an off-host transfer.

When creating PowerShell scripts, remember that variable names are case-insensitive; avoid overwriting automatic names such as `$HOME` or `$Args`. Before scripted replacement verify the expected match count, stop on failed prerequisites, inspect the changed-file diff and run a whitespace/diff check. Do not proceed with destructive commands after an earlier failed step. For source cleanup, identify actual callers/references and remove **only obsolete artifacts of the accepted change**, not neighboring modules just because their names look redundant. Final verification applies to the cleaned candidate, not only its first working draft.

## Targeted UI specialization — not separate worker roles

**Admin:** identify Filament Page/Resource/Concern, common component and the actual rendered Blade. Preserve one shell/scroll/dialog lifecycle, central control and table geometries, stable selection/ordering/drag semantics, keyboard/focus, Audited Working mutation and truthful notifications. No shadow page-local visual grammar.

**Public:** inspect canonical route, SiteSection/publication eligibility, shared menu and paper/frame, responsive content shell, image/video rights, working Preview versus Committed/LIVE, and exact accepted presentation. Navigation changes must not create duplicate DOM ownership or jump; responsive bugs require layout ownership fixes rather than timers or magic sizes.

## Make repeated feedback durable

A recurring user correction that reveals a reusable implementation rule belongs in **this existing role skill**, even if it was discovered during a feature task. Amend the governing paragraph (or shared worker protocol for cross-role behavior), rather than recording it only in a disposable worker file, appending another prohibition at the bottom or creating a parallel manual. A feature-specific accepted invariant belongs in its **one** canonical product contract through Docs ownership; the active Dev worker may report the exact proposed wording for approved integration. Before changing a rule, check whether it already exists and whether the new complaint is evidence of a distinct failure. If a proposal conflicts with established guidance, present the conflict and let the user choose; do not overwrite the decision quietly.

## Finish and handoff

For multi-step assignments with an explicit completion goal, do not treat a successful first patch or intermediate report as the end. Continue through the authorized remaining work and targeted checks without waiting for repeated "weiter" messages, stopping only for a real approval/blocker or completed outcome. See the [shared continuous-work rule](../../README.md#continuous-work-and-integration-gates).

Re-read fresh `dev` HEAD and claimed worker scope before writing; use safe non-force expected-head commit and reconcile parallel Dev workers. Record the exact source change and verification class (**inspected**, **executed**, **browser reviewed**, **user accepted**), checked base/head revision, affected files, a compact mapping of each user requirement to implemented/not implemented, justified deviations, unresolved risks and specifically out-of-scope findings in your **own active worker record**, replacing stale notes rather than appending a diary. For visual work state which accepted reference implementations and shared Blade/CSS primitives were reused; list any justified new feature styles. Do not claim tests or browser acceptance that were not performed. User-authorized freezes and selective transfers to other branches are separate.
